# jev-benchmark — Jev 判定層のベンチマーク(再現手順つき)

meiseki の文脈判断(G 定型句の実質・H 段落反復・A litotes)を Jev(TypeSafe AI の decision-only モデル)に任せた場合の、速度と判定一致率を測る実験です。

対象データ・測定スクリプト・過去の生データをここに置いてあり、キーを設定すれば誰でも同じ条件で再現できます。

## 構成

| ファイル | 内容 |
|---|---|
| `cases.json` | 既知の正解を持つ 8 事例(G 3 問・H 3 問・A 2 問)。正解の根拠は `examples/meiseki` と SKILL.md のガードレール。採用帯(p ≥ 0.8 / p ≤ 0.2)もここで定義 |
| `llm-baseline-prompt.txt` | LLM ベースライン測定に使うプロンプト(同じ 8 問を 1 プロンプトにまとめたもの) |
| `results/<日付>/` | 実測の生データ(測定コマンドの出力・API の生レスポンス・LLM の回答と実時間) |

## 再現手順

前提: リポジトリのルートで実行する。Jev の API キーを設定しておく(`npm run jev:setup`。未設定だと測定は exit 3 で止まる)。

```bash
# 1. 単問モード(1 問 = 1 リクエスト x 8)
npm run bench:jev

# 2. バッチモード(8 問を 1 リクエスト。スキルの実運用形)
npm run bench:jev -- --batch

# 3. LLM ベースライン(同じ 8 問を claude -p で解かせ、実時間を測る)
time claude -p "$(cat experiments/jev-benchmark/llm-baseline-prompt.txt)"
```

出題セットを差し替えたい場合は、環境変数 `JEV_BENCH_CASES` に別の JSON のパスを渡す(形式は `cases.json` と同じ)。

## 実測結果(2026-10-11・jev-1.13.0)

生データは `results/2026-10-11/` にある。

| 方式 | 8 問の所要時間 | 生の一致率 | 採用帯での成績 |
|---|---|---|---|
| Jev バッチ | 218〜260ms | 7/8〜8/8 | 採用 5 問・正解 5/5・差し戻し 3 問 |
| Jev 単問 ×8 | 合計 2.0〜4.6 秒 | 6/8 | 採用 5 問・正解 5/5・差し戻し 3 問 |
| LLM(claude -p) | 14.8〜21.1 秒(中央値 18.0 秒) | 8/8 | — |

読み取れること:

- バッチは単問 1 回とほぼ同じ時間で 8 問を返す。LLM 比でおよそ 70 分の 1
- 確信の強い判定(p ≥ 0.8 / p ≤ 0.2)は実行をまたいで安定し、全問正解だった
- 不確信帯(0.2 < p < 0.8)の確率値は実行ごとに揺れる(例: litotes の問題で 0.46〜0.71)。この帯を採用せず LLM へ差し戻す設計の根拠になっている
- LLM は全問正解だが、CLI 起動込みで約 18 秒かかる

この結果に基づき、スキルの採用帯は p ≥ 0.8 / p ≤ 0.2 に設定した(meiseki SKILL.md に反映済み)。

2026-10-12 の再測定(`results/2026-10-12/meiseki-noul-rerun.txt`)では、バッチの生一致が 3 回とも 8/8 に改善し、採用帯の誤りは引き続き 0 だった。LLM 側は 9〜18 秒と日次で振れるため、速度差は約 30〜70 倍のレンジで読むのが正確である(Jev 側は両日とも 218〜330ms で安定)。

同日、事例の少なさによるブレを抑えるため判定セットを 8 → 20 問に拡張した(`results/2026-10-12/expanded-20.txt`)。結果は次のとおりで、設計の主張がより強い裏付けを得た。

- 20 問の一括判定も 276〜325ms で、8 問時と同じ時間だった(問題数を 2.5 倍にしても Jev 側のコストは増えない)
- 生の一致は 3 回とも 17/20(85%)。誤り 3 件はすべて A(畳める二重否定)で確率 0.55〜0.66 の不確信帯にあり、全件が LLM へ差し戻された
- 採用帯の判定は 3 回累計 36 問・誤り 0。litotes 系の苦手は系統的だが、常に差し戻し側へ落ちるため実害がない
- LLM は 23.0〜24.2 秒で 19〜20/20。20 問での速度差は中央値どうしで約 77 倍

## yorisoi の score 検証(2026-10-12 実測)

`cases-yorisoi.json` と `results/2026-10-12/yorisoi-score.txt` に、文書レベル判定(score 型)の検証を収録した。examples/yorisoi の before/after 6 文書を N5〜N1 のルーブリックで採点させた結果:

- before と after の難易度順序は 3 ペアすべて正しい(before > after)
- 仮置きの期待帯との一致は 4/6。外れた 2 件のうち 02-before は表記規則の違反が主で語彙は平易なため、判定(N4)の側が妥当とも読める
- レイテンシは平均 387ms/文書(6 文書の直列で約 2.3 秒)。信頼度は 0.70〜0.84
- LLM ベースライン(claude -p・同じ 6 文書・3 回)は中央値 20.7 秒で、帯一致 6/6・ペア順序 3/3。速度は Jev が約 9 倍、絶対帯の精度は LLM が上という、meiseki の noul 検証と同じ構図になった
- score 型の返り値は N ラベルではなく「ルーブリック配列の位置(0 始まりの数値)」である。換算を忘れると「0.77 相当」のような表示になる(vocab-check は換算済み)
- 対照として、同じやさしい文書(01-after)を jReadability 近似は「N1 超」と大きく外し、Jev は「N4」と目標どおりに当てた

## 注意

- `cases.json` の例文には、検出対象を示すための「わざと悪い日本語」が含まれる
- 8 事例は小さなサンプルなので、結果は目安として扱う。事例を足す場合は、正解を `examples/meiseki` の before/after のように根拠づけてから `cases.json` へ追加する
- 測定には Jev API の利用料がかかる(入力のみ課金。この 8 問なら 1 回あたり 1 円未満)
