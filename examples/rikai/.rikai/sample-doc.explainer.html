7/ 7 論点に挑戦済み

復習中：一意キーと重複の防止、再送対象の判定（502/503/タイムアウト）、完了判定と保存失敗

2.1 重複の防止復習中

同じキーで 2 度頼むと？

同じ引換番号で何度たずねても、出てくる注文票は最初の 1 枚。

きちんと言うと送信要求には、呼び出し元が利用者 ID と通知種別から作った一意キーを付けます。同じキーの要求をもう一度受け付けると、ワーカーは新しいジョブを作らず、既存ジョブの ID を返します。呼び出し元が再送でキーを作り直すと、別のジョブとして扱われます。

迷いどころ新しいジョブができるのは、キーを作り直した要求のときだけです。同じキーのままなら、何度届いてもジョブは増えず、返る ID も既存ジョブのものです。見分ける目印は、キーが同じかどうかです。
教科書の言葉

「同じキーを持つ要求を再度受け付けた場合、ワーカーは新しいジョブを作らず、既存ジョブの ID を返す。」

2.2 配信順序卒業

保存の順は、完了の順？

列には並んだ順に入れる。でも前の人が忘れ物で戻れば、後ろの人が先に店を出る。

きちんと言うとワーカーは同じ利用者へのジョブを受付順に保存しますが、配信の完了順は保証しません。先に受け付けたジョブが再送待ちになると、後のジョブが先に完了することがあります。

迷いどころ受付順が守られるのは「保存」までです。「完了」の順は、再送待ちが入ると入れ替わります。後のジョブが先に完了しうるのは、先のジョブが再送待ちになったときです。
教科書の言葉

「ワーカーは同じ利用者へのジョブを受付順に保存するが、配信の完了順は保証しない。」

3.1 再送の対象復習中

どの失敗なら再送する？

話し中や圏外なら、かけ直せばつながるかもしれない。番号違いなら、何度かけても同じ。

きちんと言うと外部 API が 502 または 503 を返した場合と、接続がタイムアウトした場合は再送します。これらは一時的な失敗として扱います。429 を除く 4xx 応答は再送せず、失敗として確定します。

迷いどころ応答が返ったかどうかでは分かれません。503 は応答が返っていても、一時的な失敗として再送します。エラー応答がすべて再送の対象になるわけでもなく、429 を除く 4xx は再送しません。見分ける目印は応答コードです。
教科書の言葉

「外部 API が 502 または 503 を返した場合と、接続がタイムアウトした場合は再送する。これらは一時的な失敗として扱う。」

3.1 再送の対象卒業

4xx の中の 429 は？

「全員、上履きに履き替える。ただし 1 人だけ例外」の 1 人が 429。

きちんと言うと429 を除く 4xx 応答は、要求内容を変えないまま再送しても成功が見込めないため、再送せずに失敗として確定します。429 は、この「再送しない」の規則から外れます。429 を再送するかどうかは、原文には書かれていません。

教科書の言葉

「429 を除く 4xx 応答は再送しない。」

3.2 待機時間と上限卒業

何回まで、どれだけ待つ？

返事のない家は、間をあけながら初回も数えて 5 回までノックする。それでもだめなら伝言箱へ。

きちんと言うと再送前の待機時間は 1 秒、2 秒、4 秒の順に延ばし、その後は 8 秒を上限とします。試行回数は初回送信を含めて最大 5 回です。5 回目が失敗したジョブは自動では再送せず、失敗キューへ移します。

教科書の言葉

「再送前の待機時間は 1 秒、2 秒、4 秒の順に延ばし、その後は 8 秒を上限とする。」

「初回送信を含む試行回数は最大 5 回とする。」

4.1 完了の判定復習中

いつ「完了」になる？

荷物を手渡しても、控えを台帳にしまうまでは配達完了にしない。

きちんと言うと外部 API が成功応答を返し、その応答 ID を配信記録へ保存できた時点で、ジョブを完了とします。成功応答を受け取っても保存に失敗した場合は完了にしません。保存に失敗したジョブを再実行するときも、受付時の一意キーを引き継ぎます。

迷いどころ外部 API の成功応答は、完了の条件の片方にすぎません。もう片方は、応答 ID を配信記録へ保存できたことです。成功応答を受け取っていても、保存に失敗すれば完了ではありません。
教科書の言葉

「成功応答を受け取っても保存に失敗した場合は完了にしない。」

4.2 運用停止卒業

止めるとき、送信中の要求は？

閉店時間でも、レジの途中の会計は済ませてから閉める。火事なら会計の途中でも外へ出る。

きちんと言うと運用者が配信を停止すると、新しいジョブの取得を止めます。すでに外部 API へ送信中の要求は取り消さず、その応答を記録してからワーカーを停止します。ただし、情報漏えいのおそれがある緊急停止では、送信中の要求も直ちに中断します。

教科書の言葉

「すでに外部 API へ送信中の要求は取り消さず、その応答を記録してからワーカーを停止する。」

「ただし、情報漏えいのおそれがある緊急停止では、送信中の要求も直ちに中断する。」
