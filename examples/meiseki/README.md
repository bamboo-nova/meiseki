# meiseki 適用例（Before / After）

`meiseki` を実際の日本語にかけた例を集めた。各例は `NN-name.before.md`（原文）と `NN-name.after.md`（明晰化後）の対で置いてある。
読解負荷スコア（RLS。低いほど読みやすい）は同梱の `.agents/skills/meiseki/references/textlint.config.json` で textlint を実行して測った実測値。

| # | 例 | 主に効いたカテゴリ | RLS (before → after) |
|---|---|---|---|
| 01 | リトライ機構の説明 | A 二重否定 / B 長文・連体修飾 / C の連鎖 / D 冗長・一般論 | **166.7 → 0.0** |
| 02 | 埋もれた列挙 | F 列挙の箇条書き化 / B 読点過多 | **200.0 → 0.0** |
| 03 | 名詞化・「の」連鎖 | C（textlint では測れない＝LLM 判断） | 0.0 → 0.0 ※ |
| 04 | 飾りの箇条書き | E 体裁（`no-ai-list-formatting` で機械検出） | **75.0 → 0.0** |
| 05 | 元から平易な文 | （なし＝あえて触らない） | 0.0 → 0.0 |
| 06 | LLM 定型句 | G 定型句（prh 辞書で機械検出）/ D 曖昧表現（`ai-tech-writing-guideline`） | **175.0 → 0.0** |
| 07 | 段落レベルの反復 | H 段落冗長（textlint では測れない＝LLM 判断） | 0.0 → 0.0 ※ |
| 08 | 分離型・丁寧形の二重否定 | A 二重否定（`no-double-negative-ja` 未対応形を prh 補完辞書で機械検出） | **150.0 → 0.0** |
| 09 | 学術文書（混在文書） | A / G を本文だけ直し、参考文献・数式・キャプション・引用は原文のまま | **71.4 → 0.0** ※本文のみ |

※ 03・07 は RLS が動かないが、これは**欠陥ではなく設計どおり**。「の」連鎖・一般の名詞化（C の一部）、段落レベルの反復（H）は textlint では検出できず LLM が担う領域で、RLS はあくまで textlint が見える範囲の指標だからだ。改善自体は本文を見れば分かる。詳しくは各例の注を参照。
なお 04（体裁）は v0.5.0 で `textlint-rule-preset-ai-writing` を導入したことで決定論検出に変わり、RLS が動くようになった。

> 再現方法：プラグインルートで次のように実行するとスコアの素データ（指摘の JSON）が得られる。
>
> ```bash
> npx --min-release-age=7 --yes --package textlint@14.8.4 --package textlint-rule-preset-ja-technical-writing@10.0.2 --package textlint-rule-preset-ai-writing@1.1.0 --package textlint-rule-prh@6.1.0 textlint -c .agents/skills/meiseki/references/textlint.config.json -f json examples/meiseki/01-retry.before.md
> ```

## 01. リトライ機構の説明 ── 二重否定・長文・の連鎖・一般論

**Before**（`01-retry.before.md`）

> 近年、マイクロサービスアーキテクチャの採用が進む中で、サービス間通信における信頼性の確保は重要な課題となっています。本ライブラリは、ネットワーク障害が発生した際にリクエストを自動的に再送する処理を担当するリトライ機構を提供するものですが、すべてのエラーに対して再送が行われるわけではなく、再送が適切でないとされるエラーについては再送が行われないように設定することができます。また、リトライ回数の上限の設定の検討が必要となる場合があり、これを適切に設定しないとシステムへの負荷の増大を招かないとは言えません。

**After**（`01-retry.after.md`）

> 本ライブラリは、ネットワーク障害が起きたときにリクエストを自動で再送するリトライ機構です。ただし、すべてのエラーを再送するわけではありません。再送が適切でないエラーは、再送しないように設定できます。
>
> また、リトライ回数には上限の設定が必要な場合もあります。これを適切に設定しないと、システムの負荷が大きくなりかねません。

**直したところ**

- **D5 一般論前置き**：冒頭の「近年、マイクロサービス…重要な課題となっています」を丸ごと削り、要点から入る。
- **B 長い連体修飾／一文の詰め込み**：「再送する処理を担当するリトライ機構を提供するものですが…」を 1 文 1 メッセージに分割。
- **C「の」連鎖**：「リトライ回数の上限の設定の検討」をほどく。
- **D1 冗長**：「設定することができます」→「設定できます」。
- **A1 二重否定（最重要）**：「負荷の増大を招かないとは言えません」は論理的には「招くことがある」。`負荷が増えない` と畳むと**意味が反転する誤訳**になるため、`負荷が大きくなりかねません`（＝増えうる）へ正しく畳んでいる。

## 02. 埋もれた列挙 ── F：箇条書きに開く

**Before**（`02-buried-list.before.md`）

> このコマンドは、設定ファイルの読み込み、環境変数の展開、依存パッケージの解決、そしてビルドキャッシュの初期化を順番に行ってから、実際のコンパイル処理に入ります。

**After**（`02-buried-list.after.md`）

> このコマンドは、コンパイルの前に次の4つを順番どおり行います。
>
> - 設定ファイルの読み込み
> - 環境変数の展開
> - 依存パッケージの解決
> - ビルドキャッシュの初期化

**直したところ**

- **F 列挙の構造化**：同格の 4 項目が一文に埋もれて並列関係を読み手に再構成させていた。箇条書きに開いて認知負荷を下げる。項目・順序・情報量は変えない。
- **B 読点過多**：4 つ以上の読点（`max-ten`）が一掃される。
- あえて「**太字＋コロン**」の定型にはしない（それ自体が AI っぽさの指紋になるため）。

## 03. 名詞化・「の」連鎖 ── textlint では測れない領域

**Before**（`03-nominalization.before.md`）

> 本機能の導入の目的は、運用コストの削減の実現と、障害発生時の復旧時間の短縮への寄与にあります。

**After**（`03-nominalization.after.md`）

> 本機能を導入する目的は、運用コストを削減し、障害時の復旧時間を短縮することです。

**直したところ**

- **C2「の」連鎖**：「本機能の導入の目的」「運用コストの削減の実現」をほどく。
- **C1 サ変名詞化**：「削減の実現」「短縮への寄与」を動詞（削減し／短縮する）に戻す。
- **ポイント**：これらは textlint には検出器がなく、RLS は 0.0 → 0.0 のまま動かない。だが本文は明らかに読みやすくなっている。**「textlint で取れない構文を LLM が担う」**という二層構成の価値が出る例。

## 04. 飾りの箇条書き ── E：散文に戻す

**Before**（`04-decorative-bullets.before.md`）

> 本リリースの変更点は次のとおりです。
>
> - **パフォーマンス**: 起動時間を短縮しました。
> - **そしてその結果**: ユーザー体験が向上しました。
> - **まとめると**: 全体的に使いやすくなりました。

**After**（`04-decorative-bullets.after.md`）

> 本リリースでは起動時間を短縮しました。その結果、ユーザー体験が向上し、全体的に使いやすくなりました。

**直したところ**

- **E1 飾りの箇条書き**：これは同格の列挙ではなく「短縮した → だから体験が向上 → 結果まとめ」という**因果の流れ**を無理に箇条書きに割ったもの。流れのある説明なので散文に戻す。
- **02 との対比**：02（埋もれた列挙）は箇条書きに**開き**、04（飾りの箇条書き）は散文に**畳む**。一見逆だが、統一原理は同じ「構造を内容の論理形状に合わせる」。
- **機械検出**：v0.5.0 から「太字＋コロン」のリスト定型は `ai-writing/no-ai-list-formatting` が検出する
  （before は E 3 件 ÷ 4 文 × 100 = RLS **75.0**）。散文に戻すかどうかの判断は従来どおり LLM が担う。

## 05. 元から平易な文 ── あえて触らない

**Before**（`05-already-clear.before.md`）

> このコマンドはログを消します。実行すると元に戻せないので注意してください。

**After**（`05-already-clear.after.md`）

> このコマンドはログを消します。実行すると元に戻せないので注意してください。

**直したところ：なし（意図的に）**

- 既に一読で意味が取れる文には手を入れない。全文を均質に整えると、かえって無機質な「エディタが撫でた感じ」が出る。
- 「読みにくい構文だけを削ぎ、読みやすい文は残す」という meiseki のガードレールを示す例。Before と After が完全一致しているのが正しい挙動。

## 06. LLM 定型句 ── G：prh 辞書で機械検出して削る

**Before**（`06-llm-phrases.before.md`）

> 重要なのは、リトライ回数に上限を設けることです。この設定は極めて重要であり、安定運用に不可欠な要素だと言えます。本記事では、この上限設定について多角的に掘り下げていきます。適切な上限値の選定は、システム設計の核心に他なりません。

**After**（`06-llm-phrases.after.md`）

> リトライ回数には上限を設けます。この設定は安定運用に必要です。本記事では、この上限設定を説明します。

**直したところ**

- **G1 予告と総括**：「重要なのは〜です」の予告の枠を外し、主張を直接書く。「〜に他なりません」の空虚な強調文は、直前の主張の繰り返しでもある（H1 と同根）ため削る。
- **G2 空虚な形容**：「極めて重要」「不可欠な要素」を、根拠を足さずに「必要です」へ落とす。主張の向きは変えない。
- **G3 空虚な動詞**：「多角的に掘り下げていきます」→「説明します」。本文に実際の観点が書かれていないので具体化はしない。
- **機械検出**：before では同梱の prh 辞書（`prh-llm-phrases.yml`）が 6 件（重要なのは／極めて／不可欠／多角的／掘り下げ／に他なりません）、v0.5.0 で導入した `ai-writing/ai-tech-writing-guideline` が曖昧表現（D）を 1 件検出し、計 7 件で RLS は **175.0**（guideline の総括行は数えない）。after で 0 件になる。**G は決定論層で検出でき、LLM 層が「削るか残すか」を文脈判断する**という分担の例。

## 07. 段落レベルの反復 ── H：textlint では測れない領域

**Before**（`07-paragraph-redundancy.before.md`）

> このAPIは冪等です。同じリクエストを何度送っても結果は変わりません。つまり、再送しても安全だということです。
>
> デプロイ時は、設定を読み込み、依存を解決し、キャッシュを初期化してからビルドが始まります。このように、ビルドの前には複数の準備処理が実行されます。なお、この設定は本番環境でも有効です。ステージング環境でも有効です。開発環境でも同様に有効です。

**After**（`07-paragraph-redundancy.after.md`）

> このAPIは冪等で、同じリクエストを何度送っても結果は変わりません。
>
> デプロイ時は、設定を読み込み、依存を解決し、キャッシュを初期化してからビルドが始まります。なお、この設定は本番・ステージング・開発のどの環境でも有効です。

**直したところ**

- **H1 言い換え反復**：「冪等です」「結果は変わりません」「再送しても安全」は同じ主張の三重の言い換え。一度だけ述べる。
- **H2 描写直後の再要約**：手順を述べた直後の「このように、複数の準備処理が実行されます」は情報量ゼロの再要約なので削る。
- **H3 並列事実の分散**：「本番でも／ステージングでも／開発でも有効」の三文を一文に集約する。**事実は三つとも残す**（削るのは反復であって情報ではない）。
- **ポイント**：H は textlint に検出器がなく RLS は 0.0 → 0.0 のまま。03・04 と同じく「textlint で取れない構文を LLM が担う」領域の例。文単位ではどの文も平易で、**段落単位で初めて見える冗長**を扱っている。

## 08. 分離型・丁寧形の二重否定 ── prh 補完辞書で機械検出

**Before**（`08-separated-double-negative.before.md`）

> この設定を省略した場合に、パフォーマンスへの影響がないとは言えません。既定値のままでも運用できないわけではありませんが、環境によっては応答が遅くなる可能性は否定できません。

**After**（`08-separated-double-negative.after.md`）

> この設定を省略すると、パフォーマンスに影響することがあります。既定値のままでも運用できます。ただし、環境によっては応答が遅くなることもあります。

**直したところ**

- **A1 二重否定（分離型・丁寧形）**：3 つの二重否定をすべて肯定に畳む。真偽は反転させない。
  - 「影響がないとは言えません」→「影響することがあります」
  - 「運用できないわけではありませんが」→「運用できます。ただし〜」
  - 「可能性は否定できません」→「可能性があります（〜こともあります）」
- **機械検出の背景**：この 3 形は本家 `no-double-negative-ja` では**検出されない**（実測で確認。
  同ルールは「〜ないとは限らない」等の終止形は拾うが、分離型「〜ないとは言えない」「〜は否定できない」
  「〜なくはない」「〜ないわけがない」と、丁寧形「〜ないわけではありません」等を拾わない）。
  そのため同梱の prh 辞書（`prh-llm-phrases.yml` の A1 補完セクション）で補い、before では prh が
  3 件検出して RLS **150.0**、after で 0 件になる。検出の網羅テストは
  `scripts/test-meiseki-check.sh`（`npm run test:hook`）にある。

## 09. 学術文書（混在文書）── 本文だけ直し、対象外領域は原文のまま

**Before**（`09-academic-document.before.md`）の本文

> 重要なのは、提案手法の汎化性能を確認することです。本稿では、この汎化性能について多角的に掘り下げていきます。
>
> 評価は3つのデータセットで行いました。一部の条件では性能が劣化する可能性は否定できません。また、既定の設定のままでも実運用に適用できないわけではありません。
>
> 有意水準5%で検定した結果、データセットBについては帰無仮説は否定できないことが分かりました。

**After**（`09-academic-document.after.md`）の本文

> 本稿では、提案手法の汎化性能を確認します。
>
> 評価は3つのデータセットで行いました。一部の条件では性能が劣化する場合もあります。また、既定値のままでも実運用に適用できます。
>
> 有意水準5%で検定した結果、データセットBについては帰無仮説は否定できないことが分かりました。

このファイルには本文のほかに **数式（`$...$` / `$$...$$` / `\begin{align}`）・図キャプション（`図1: 〜`）・
引用ブロック・参考文献セクション（Nature 形式 / IEEE 形式 / ASA 形式の混在）** が含まれるが、
before と after で**1 バイトも変わらない**。

**直したところ（本文のみ）**

- **G1 予告**：「重要なのは〜です」の枠を外し主張を直接書く。
- **G3 空虚な動詞**：「多角的に掘り下げていきます」→「確認します」。
- **A1 二重否定（分離型・丁寧形）**：「可能性は否定できません」→「場合もあります」、
  「適用できないわけではありません」→「適用できます」。真偽は反転させない。

**残したところ（SKILL.md §3 の対象外領域）**

- **統計の術語**：「帰無仮説は否定できない」は検定の結論であり、肯定に畳むと**統計的な意味が壊れる**。
  prh 辞書は「仮説」が直前にある場合をパターンで除外しており（negative lookbehind）、
  before でも after でも検出しない。after に「否定できない」が残っているのが**正しい挙動**。
- **参考文献・数式・キャプション・引用**：エントリのフォーマット（Nature / IEEE / ASA / 和文）を問わず原文のまま。
  直接 textlint をかけると和文の参考文献行だけで 4 件（連続漢字 ×2、prh ×2）出るが、
  これは対象外領域なので **hook は lint 前にマスクして 0 件として扱う**。

**RLS と hook の見え方**

- RLS（本文のみで算出）：before **71.4**（prh 5 件 ÷ 7 文 × 100）→ after **0.0**。
- hook 判定：before は **block**（本文の prh 5 件 = A1 ×2 ＋ G1 ×1 ＋ G2/G3 ×2）。
  after は**素通り**。本文が良くなれば学術文書でも block されない、
  という「参考文献・数式・キャプションの誤検知修正」（v0.4.0）の動作を示す例。
