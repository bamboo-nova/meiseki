# meaning-benchmark — 意味の検算の所要時間(再現手順つき)

meiseki の Step 5(意味の検算)で使う `meiseki-invariants.js` が、どれだけ時間を足すかを測る実験です。書き換えの前後で数値・識別子・否定・条件・確度などの印を数えて比べる処理で、ネットワークも API キーも使いません。

meiseki の処理速度は使い続けてもらえるかを左右するため、基準を決めて測っています。基準は、既存のワークフローで書き換えの前後に必ず 1 回ずつ走る textlint の 1 回分です。

## 構成

| ファイル | 内容 |
|---|---|
| `../../scripts/bench-meaning.js` | 測定スクリプト(`npm run bench:meaning`) |
| `results/<日付>/bench.json` | 実測の生データ(測定環境と、文書ごとの中央値・最大値) |

## 測り方

- スキルが実際に呼ぶ形(`node` のプロセス起動込み)で、各文書を 5 回測って中央値と最大値をとる
- 文書は 4 種類
  - `examples/meiseki` の 9 組(平均 185 文字。書き換えの前後が実在する短い例)
  - README.md 相当(約 2.5 万字)
  - README を 4 回つないだもの(約 10 万字)
  - README を 10 回つないだもの(約 25 万字)
- 長い文書の書き換え後の版は、本文の段落だけを機械的に変えて作る。11 段落に 1 つを削除し、7 段落に 1 つを分割し、冗長表現を言い換える。段落の対応づけに負荷をかけるためで、コードブロックなどは変えない
- 比較の基準として、同じ文書に textlint を 1 回かけた時間も測る(npx のキャッシュを温めてから 3 回の中央値)

## 再現手順

リポジトリのルートで実行する。

```bash
npm run bench:meaning                      # 検算と textlint の両方を測る
npm run bench:meaning -- --no-textlint     # 検算だけを測る(数秒で終わる)
npm run bench:meaning -- --runs 10 --save experiments/meaning-benchmark/results/<日付>/bench.json
```

## 実測結果(2026-11-14・Apple M1・Node v24.15.0)

生データは `results/2026-11-14/bench.json` にある。

| 文書 | 文字数 | 検算(中央値 / 最大) | textlint 1 回 | 比 |
|---|---:|---:|---:|---:|
| examples/meiseki 9 組(1 組あたり) | 185 | 30 / 38 ms | 4,471 ms | 0.7% |
| README.md 相当 | 24,734 | 115 / 117 ms | 4,978 ms | 2.3% |
| README ×4 | 98,942 | 378 / 387 ms | 8,581 ms | 4.4% |
| README ×10 | 247,358 | 882 / 884 ms | 26,247 ms | 3.4% |

- 検算の時間は文字数にほぼ比例する。25 万字でも 1 秒を切る
- どの大きさでも textlint 1 回の 5% 未満に収まる。textlint は書き換えの前後で 2 回走るので、ワークフロー全体から見た割合はさらに小さい
- textlint の時間は npx の起動の揺れで回ごとに数秒ぶれる。比はその範囲の目安として読む

## 時間が増える場合

検算そのものの時間とは別に、`恐れあり` が出たときだけ、該当する段落を LLM が 1 回直す手間が加わる。直しは 1 回までで、再検査でも残れば段落を原文に戻す。原文に戻す処理はスクリプトが行うので、ここに LLM の時間は加わらない。

`恐れあり` がどれだけ出るかは、次のとおり確かめた。

- `examples/meiseki` の 9 組(意味を保った書き換え): 0 件
- 長い文書の機械的な書き換え(上の測り方と同じ): 段落の削除で消えた数値・識別子と、「」・インラインコードの中身の変化だけを検出した。どちらも正しい検出で、それ以外の誤検出は 0 件
- 意味を変えた書き換え(`examples/meaning/` の 7 種類): すべて検出

ただし、規則は `examples/meiseki` の 9 組を見ながら調整した。実際の書き換えでの誤検出率は、もっと多くの組で測る必要がある。

## 過去の改善

- 段落の対応づけで、探す範囲(帯の幅)を「25 + 前後の段落数の差」から「30 + 差の 1/8」に絞った。帯の中心は段落数の比で補正しているので、幅を絞っても対応づけの結果は変わらない(テスト 24 件すべて同じ結果)
