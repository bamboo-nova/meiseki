# meiseki 適用例（Before / After）

`meiseki` を実際の日本語にかけた例を集めた。各例は `NN-name.before.md`（原文）と `NN-name.after.md`（明晰化後）の対で置いてある。
読解負荷スコア（RLS。低いほど読みやすい）は同梱の `.textlintrc.json` で textlint を実行して測った実測値。

| # | 例 | 主に効いたカテゴリ | RLS (before → after) |
|---|---|---|---|
| 01 | リトライ機構の説明 | A 二重否定 / B 長文・連体修飾 / C の連鎖 / D 冗長・一般論 | **100.0 → 0.0** |
| 02 | 埋もれた列挙 | F 列挙の箇条書き化 / B 読点過多 | **200.0 → 0.0** |
| 03 | 名詞化・「の」連鎖 | C（textlint では測れない＝LLM 判断） | 0.0 → 0.0 ※ |
| 04 | 飾りの箇条書き | E 体裁（textlint では測れない＝LLM 判断） | 0.0 → 0.0 ※ |
| 05 | 元から平易な文 | （なし＝あえて触らない） | 0.0 → 0.0 |

※ 03・04 は RLS が動かないが、これは**欠陥ではなく設計どおり**。「の」連鎖・一般の名詞化（C の一部）や体裁（E）は textlint では検出できず LLM が担う領域で、RLS はあくまで textlint が見える範囲の指標だからだ。改善自体は本文を見れば分かる。詳しくは各例の注を参照。

> 再現方法：`cd ..`（プラグインルート）で `npm install` 後、
> `npx textlint -c .textlintrc.json -f json examples/01-retry.before.md` のように実行するとスコアの素データ（指摘の JSON）が得られる。

## 01. リトライ機構の説明 ── 二重否定・長文・の連鎖・一般論

**Before**（`01-retry.before.md`）

> 近年、マイクロサービスアーキテクチャの採用が進む中で、サービス間通信における信頼性の確保は重要な課題となっています。本ライブラリは、ネットワーク障害が発生した際にリクエストを自動的に再送する処理を担当するリトライ機構を提供するものですが、すべてのエラーに対して再送が行われるわけではなく、再送が適切でないとされるエラーについては再送が行われないように設定することができます。また、リトライ回数の上限の設定の検討が必要となる場合があり、これを適切に設定しないとシステムへの負荷の増大を招かないとは言えません。

**After**（`01-retry.after.md`）

> 本ライブラリは、ネットワーク障害が起きたときにリクエストを自動で再送するリトライ機構です。ただし、すべてのエラーを再送するわけではありません。再送が適切でないエラーは、再送しないように設定できます。
>
> また、リトライ回数には上限の設定が必要な場合もあります。これを適切に設定しないと、システムの負荷が大きくなりかねません。

**直したところ**

- **D5 一般論前置き**：冒頭の「近年、マイクロサービス…重要な課題となっています」を丸ごと削り、要点から入る。
- **B 長い連体修飾／一文の詰め込み**：「再送する処理を担当するリトライ機構を提供するものですが…」を 1 文 1 メッセージに分割。
- **C「の」連鎖**：「リトライ回数の上限の設定の検討」をほどく。
- **D1 冗長**：「設定することができます」→「設定できます」。
- **A1 二重否定（最重要）**：「負荷の増大を招かないとは言えません」は論理的には「招くことがある」。`負荷が増えない` と畳むと**意味が反転する誤訳**になるため、`負荷が大きくなりかねません`（＝増えうる）へ正しく畳んでいる。

## 02. 埋もれた列挙 ── F：箇条書きに開く

**Before**（`02-buried-list.before.md`）

> このコマンドは、設定ファイルの読み込み、環境変数の展開、依存パッケージの解決、そしてビルドキャッシュの初期化を順番に行ってから、実際のコンパイル処理に入ります。

**After**（`02-buried-list.after.md`）

> このコマンドは、コンパイルの前に次の4つを順番どおり行います。
>
> - 設定ファイルの読み込み
> - 環境変数の展開
> - 依存パッケージの解決
> - ビルドキャッシュの初期化

**直したところ**

- **F 列挙の構造化**：同格の 4 項目が一文に埋もれて並列関係を読み手に再構成させていた。箇条書きに開いて認知負荷を下げる。項目・順序・情報量は変えない。
- **B 読点過多**：4 つ以上の読点（`max-ten`）が一掃される。
- あえて「**太字＋コロン**」の定型にはしない（それ自体が AI っぽさの指紋になるため）。

## 03. 名詞化・「の」連鎖 ── textlint では測れない領域

**Before**（`03-nominalization.before.md`）

> 本機能の導入の目的は、運用コストの削減の実現と、障害発生時の復旧時間の短縮への寄与にあります。

**After**（`03-nominalization.after.md`）

> 本機能を導入する目的は、運用コストを削減し、障害時の復旧時間を短縮することです。

**直したところ**

- **C2「の」連鎖**：「本機能の導入の目的」「運用コストの削減の実現」をほどく。
- **C1 サ変名詞化**：「削減の実現」「短縮への寄与」を動詞（削減し／短縮する）に戻す。
- **ポイント**：これらは textlint には検出器がなく、RLS は 0.0 → 0.0 のまま動かない。だが本文は明らかに読みやすくなっている。**「textlint で取れない構文を LLM が担う」**という二層構成の価値が出る例。

## 04. 飾りの箇条書き ── E：散文に戻す

**Before**（`04-decorative-bullets.before.md`）

> 本リリースの変更点は次のとおりです。
>
> - **パフォーマンス**: 起動時間を短縮しました。
> - **そしてその結果**: ユーザー体験が向上しました。
> - **まとめると**: 全体的に使いやすくなりました。

**After**（`04-decorative-bullets.after.md`）

> 本リリースでは起動時間を短縮しました。その結果、ユーザー体験が向上し、全体的に使いやすくなりました。

**直したところ**

- **E1 飾りの箇条書き**：これは同格の列挙ではなく「短縮した → だから体験が向上 → 結果まとめ」という**因果の流れ**を無理に箇条書きに割ったもの。流れのある説明なので散文に戻す。
- **02 との対比**：02（埋もれた列挙）は箇条書きに**開き**、04（飾りの箇条書き）は散文に**畳む**。一見逆だが、統一原理は同じ「構造を内容の論理形状に合わせる」。
- これも E は textlint では測れないため RLS は 0.0 → 0.0。

---

## 05. 元から平易な文 ── あえて触らない

**Before**（`05-already-clear.before.md`）

> このコマンドはログを消します。実行すると元に戻せないので注意してください。

**After**（`05-already-clear.after.md`）

> このコマンドはログを消します。実行すると元に戻せないので注意してください。

**直したところ：なし（意図的に）**

- 既に一読で意味が取れる文には手を入れない。全文を均質に整えると、かえって無機質な「エディタが撫でた感じ」が出る。
- 「読みにくい構文だけを削ぎ、読みやすい文は残す」という meiseki のガードレールを示す例。Before と After が完全一致しているのが正しい挙動。
