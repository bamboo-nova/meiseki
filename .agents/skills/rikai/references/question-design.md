# 問題設計

## 1. 論点の抽出

資料を通読し、独立して正誤を判定できる内容を論点にする。論点は次の順で探す。

1. **主張**：書き手が読者に理解してほしい結論、推奨、因果関係、定義を抽出する。
2. **前提**：主張が成り立つ条件、対象範囲、依存関係、手順の順序を抽出する。
3. **例外**：通常則が適用されない場合、制限、禁止事項、境界条件を抽出する。

一つの論点に複数の独立した判断を詰め込まない。正答の根拠を一つの段落または連続する短い範囲から示せない内容は分割する。

論点数は短い資料で 5〜8 個、長い資料では主要な章ごとに 3〜5 個を目安とする。数を満たすために周辺的な記述を問題化せず、主張・前提・例外を優先する。

各論点には安定した `topic-NNN` 形式の id と、人が読んで内容が分かる短い題名(`title`。例「RPO と RTO の区別」)を付ける。題名は、その論点を最初に抽出したセッションの言語で書き、以後は書き換えない。削除済み id は再利用せず、資料内で一意にする。

## 2. 原文アンカー

論点ごとに、見出し階層を上位から並べた `heading_path` と、根拠段落の先頭から取った `quote` を記録する。この組を段落の主キーとし、`line` は人が探すための参考値としてだけ記録する。

`quote` は同じ見出し内で段落を一意に特定できる長さにする。要約や言い換えではなく原文の先頭と一致する文字列を使い、答え全体を露出するほど長くしない。

## 3. 選択式問題の作り方

問題文と選択肢は、ユーザーの言語で書く（SKILL.md §2）。原文から引く語句は資料の言語のままでよい。挑戦履歴の `aspect` に書く観点名は、モデルが書いたままの言語でよい。

問題は一つの論点と一つの観点だけを問う。選択肢は原則 3 個とし、正答を 1 個、ディストラクタを 2 個にする。複数正答になる場合は問題文または選択肢を直す。

問題文だけで何を判断するかが分かるようにし、「正しいものを選んでください」だけで済ませない。否定形を使う必要がある場合は「誤っているもの」のような判定方向を明示する。

正答は原文から直接根拠を示せる内容にする。原文より強い断定、条件の省略、例外の一般化を正答にしてはならない。

## 4. ディストラクタ設計

ディストラクタには、原文を急いで読んだときに起こり得る誤読を使う。もっともらしさは必要だが、資料外の知識、語呂、選択肢の長さだけで見抜ける差は使わない。

使える誤読の型は、条件と結論の逆転、対象範囲の拡大、必要条件と十分条件の混同、例外の見落とし、手順の順序違い、相関と因果の混同である。原文にない固有名詞や極端な断定を足して誤答を作ってはならない。

選択肢は文法、長さ、具体性をできるだけ揃える。「常に」「絶対に」のような語が正誤を漏らす場合は使わない。

## 5. 問題と選択肢の並び順（正解位置の分散）

問題の順番は無作為にする。復習問題を先頭に固めると、どれが復習問題かが解く前に分かってしまう。`python3` がある場合は `scripts/build_quiz.py` が問題の順番を並べ替え、問題番号を振り直す。`python3` がなくテキストだけで提示する場合は、モデルが復習問題と新しい論点の問題を混ぜて並べる。問題文に「復習」などと書かない。復習問題だったことは、採点後の結果の表で伝える。

正解を毎回同じ位置(特に先頭)に置いてはならない。位置の並びを覚えられると、理解の測定にならないためである。フォームでは 1 ページに全問が並ぶので、1 問の正解から残りの正解の位置が推測できる並べ方もしてはならない。`scripts/build_quiz.py` の無作為な並べ替えは、この条件を満たす。

`python3` がある場合、モデルは問題も選択肢もどの順で書いてよい。`scripts/build_quiz.py` が各問の選択肢を無作為に並べ替え、新しい順に `id` を `a`、`b`、`c` と振り直し、`correct` を同じ選択肢に付け替えて、出題データに書き戻す。モデルは正解の位置を計算しない。挑戦履歴の `choices` には、書き戻したあとの出題データの並び順を記録する(位置を後から復元できるようにするため)。

ブラウザを使えず問題をテキストで提示する場合も、`python3` があれば先に `scripts/build_quiz.py` を実行する(できたフォームは使わない)。テキストで提示するときは、その直前に出題データを読み直し、書かれている順と id のまま提示する。書き戻す前の並びで提示すると、ユーザーの回答が並べ替え後の `correct` と照合され、誤って採点される。

問題をテキストだけで提示する場合で、`python3` もないときに限り、モデルが正解の位置を決める。シェルが使える環境では `date +%s` で epoch 秒を取得し、使えない環境では現在日時の秒と分を使う。セッション内の i 問目(0 始まり)の正解位置は `(epoch + i) mod n`(n は選択肢数、位置は 0 始まり)とする。この回転は、1 問の正解から残りの位置を推測できる並べ方である。並べ替えのスクリプトを使えないこの経路に限り、それを受け入れる。この場合は提示した順をそのまま挑戦履歴の `choices` に記録する。

選択肢の id は、回答コード（`1:b 2:a`）でそのまま使うため、半角の小文字英数字に限る。`python3` がなくテキストだけで提示する場合は、提示する順に `a`、`b`、`c` と振る。

ディストラクタどうしの並びは自由でよいが、長さや形式の差で正解が浮かないことを §4 のとおり確認する。

## 6. 観点の付け方

挑戦履歴の `aspect` には、何を理解できるかを短く記録する。例は「主張の識別」「適用条件」「例外条件」「因果関係」「手順の順序」「具体例への適用」である。

表現だけを変えて同じ判断を求める問題は、同じ観点として扱う。観点名を変えるだけでは別角度にならない。

## 7. 別角度再出題の判定規則

再出題前に、その論点の全挑戦履歴から過去の `question`、`aspect`、`choices` を読む。直前の履歴だけを見て判定してはならない。

次の順で新しい問題を設計する。

1. 過去に使っていない観点があれば、その観点を優先する。
2. 未使用の観点が複数あれば、主張の理解に近いものから、前提、例外、適用の順に選ぶ。ただし資料の構造に合わない観点は作らない。
3. 使える観点をすべて出題済みなら、最も古く出題した観点を選び、問い方を変える。

問い方は、定義や主張を直接選ぶ「識別」、条件を満たす場面を選ぶ「適用」、誤った一般化を見抜く「反例」、因果や手順の欠落部分を選ぶ「関係」のような、回答時に必要な判断操作で区別する。

新しい問題が別角度と認められる条件は、未使用の観点を問うこと、または観点が尽きた場合に過去と異なる問い方を使うことのどちらかである。同じ根拠文について語順や同義語だけを変えた問題、正答の位置だけを変えた問題、過去と実質的に同じ選択肢を並べ替えた問題は別角度と認めない。

観点が尽きて問い方を変える場合も、過去の選択肢をそのまま再利用しない。原文に沿う範囲で、条件の適用例、例外の判別、因果関係の一部など、別の判断を必要とする選択肢を作る。原文から別の問い方を作れない場合は無理に出題せず、その論点を保留して他の論点へ進む。

作成後に過去の問題文・観点・選択肢と照合し、上の条件を満たすことを確認してから提示する。
